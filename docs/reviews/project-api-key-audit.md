# Project-Scoped API Key System — P0 Read-Only Audit

Date: 2026-08-10. Scope: `Valori-Kernel` (public) + `valori-ui` (private,
`/Users/as-mac-0272/Desktop/sass/valori-ui`). No source was modified to
produce this document — every claim below is either a direct file:line
citation (**verified**), a reasoned conclusion from adjacent verified code
(**inferred**), or explicitly flagged as **unknown**.

**Headline finding, stated up front because it changes the shape of the
work**: two unrelated, already-live API-key systems exist today, and
**neither one is project-scoped**. Local/Studio keys (`vk_...`) are scoped to
a single node process (no project concept exists at that layer at all).
Cloud keys (`vlk_...`) are scoped to an **organization**, not a project —
`verify_api_key()` accepts a `target_project_id` as a request parameter and
merely checks that project belongs to the key's org, which means any Cloud
key today can already reach every project in its org by passing a different
id. This is the exact anti-pattern the request explicitly says not to build
around. Building the project-scoped primitive is net-new work on both
sides, not a refactor of an existing project-scoped table.

## 1. Where `ProjectId` is defined

**Verified.** `crates/valori-domain/src/id.rs:128` —
`pub struct ProjectId(Uuid)`, a `#[serde(transparent)]` newtype wrapping
`uuid::Uuid`. Extensive doc comment at lines 60–125 states explicitly:
*"Not a secret. It appears in URLs and logs. Authorization is a Cloud
concern and is never implied by possession of an id."* — i.e. the type's own
documentation already anticipates that key-based authorization is a
separate, not-yet-built layer.

The same doc comment (lines 108–112) names **four existing representations**
of "project identity" that this type was meant to eventually unify:
`valori-daemon` (`ProjectManifest.id`, a UUID `String`), `valori-metadata`
(keyed on `name`), `ui/src/lib/server/projects.ts`, and "the Cloud `projects`
table." `ARCHITECTURE_AUDIT.md:368` (a prior audit already in this repo)
calls this exact fragmentation "❌ worst offender — §9" and defines migration
risk **R2** (`ARCHITECTURE_AUDIT.md:904`) for unifying them. That migration
is only partially done (see §3 below) — this system was never finished.

## 2. Where `ProjectId` is generated

**Verified.** `ProjectId::new()` → `Uuid::new_v4()`
(`crates/valori-domain/src/id.rs:362`). Only used in tests today
(`valori-domain/tests/*.rs`) — **no production code path constructs a
`valori_domain::ProjectId` yet.** Production project creation uses two
*different* id generators, neither of which is this type:

- `valori-daemon`: `crates/valori-daemon/src/lib.rs:47-49` —
  `pub fn new_id() -> String { uuid::Uuid::new_v4().to_string() }`, a bare
  string, not the `ProjectId` newtype.
- Cloud: Postgres `gen_random_uuid()` default on the `projects.id` column
  (`valori-ui/supabase/migrations/20260721120000_schema.sql:50`) — a
  completely independent UUID space with no relation to the daemon's id.

**These two id spaces do not overlap.** A local project's id and a Cloud
project's id are generated by different systems and there is no adapter
that maps one to the other. `ARCHITECTURE_AUDIT.md:1019` (milestone **M2**)
describes the intended fix ("canonical `Project` + adapters") as **not yet
done** — `crates/valori-domain/src/project.rs:442,498,551` does define
`Project`/`LocalProject`/`ApiProject` structs, but grep across both repos
found no call site constructing a Cloud project through an `ApiProject`
adapter — Cloud project creation goes straight through Supabase's own
schema, untouched by `valori-domain` at all.

## 6. Existing API-key tables/models

**Verified — two, unrelated:**

**(a) Local/Studio** — `crates/valori-node/src/api_keys.rs`, in-memory
`KeyStore` (line 102) backed by an optional JSON file
(`load()`/`save()`, lines 195–229). `ApiKeyRecord` (line 48): `id`, `scope`
(`ReadOnly`/`ReadWrite`/`Admin`, line 17), `collection: Option<String>` (an
optional single-collection lock, **not** a project lock — this predates any
project concept at the node level), `description`, `created_at`,
`token_hash: [u8; 32]` (BLAKE3 of the raw token), `prefix` (first 8 chars,
for display). Token format: `vk_<64 hex chars>` (`generate_token()`,
line 296). **No `project_id` field exists on this struct.** **No `expires_at`
field exists.** Revocation (`revoke()`, line 176) is a hard delete from the
in-memory map + rewritten file — no `revoked_at` tombstone is kept, so a
revoked key's history is not retained.

**(b) Cloud** — `valori-ui/supabase/migrations/20260721120000_schema.sql:89-111`,
`public.api_keys`: `id uuid`, **`org_id uuid`** (FK to `organizations` —
**this is the scoping column, not `project_id`**), `name`, `key_prefix`,
`key_hash` (SHA-256, `text`), `scopes text[]`, `created_by`, `created_at`,
`last_used_at`, `revoked_at` (a real nullable timestamp — unlike the local
system, revocation here is a soft flag, not a delete). Later migrations add
`request_count`, `rate_limit_window_start`, `rate_limit_window_count`
(`20260723040000_api_usage_and_rate_limits.sql:11-14`) and
`service_account_id` (referenced in `PROGRESS.md:235`, not independently
re-verified in this pass). Token format: `vlk_<8 hex>_<24 hex>`
(`rotate_api_key()`, `20260722200000_api_key_verify_and_rotate.sql:70-72`).
**No `project_id` column exists on this table either** — a key is scoped to
`org_id` only, and the association to a specific project happens
per-request, not per-key (see §7).

## 7. Existing API authentication middleware

**Verified — two, unrelated, matching §6's split.**

**(a) Local** — `auth_guard_v2` (`crates/valori-node/src/server.rs:114-151`),
an axum middleware layer. Reads `Authorization: Bearer <token>`
(line 126-129). If `AuthState::has_any_auth()` is false (no legacy token
and empty key store), auth is skipped entirely — local nodes are
unauthenticated by default. Otherwise: looks up the token in `KeyStore`
first; on hit, checks `record.scope.satisfies(required_scope)`
(`required_scope()` derives the needed scope from HTTP method + path,
lines 244-271 — e.g. `/v1/keys*`, `/v1/snapshot*`, `/v1/storage*`,
`/v1/replication*` require `Admin`; GET is always `ReadOnly`; everything
else is `ReadWrite`). Falls back to a single static "legacy" token
(`VALORI_AUTH_TOKEN` env var, constant-time compared, line 145-148) if the
key-store lookup misses. **No project scoping happens here because the
node has no project concept — a node instance already *is* one project's
data**, so the auth question is only ever "can this token touch this node
at all," never "can this token touch project X."

**(b) Cloud** — not a middleware in the traditional sense; it's a Postgres
RPC called from Next.js server code before proxying.
`valori-ui/ui/src/lib/server/project.ts:74-103`,
`resolveProjectNodeUrlByApiKey()`, calls
`supabase.rpc('verify_api_key', { full_key, target_project_id,
required_scope, p_ip })` (line 82-88). The RPC itself
(`20260722200000_api_key_verify_and_rotate.sql:8-46`) is the actual
authorization logic — **and this is where the org-vs-project gap is
concrete**: it hashes the presented key, finds the row by `key_hash`, then
does `select ... from projects where id = target_project_id and org_id =
key_row.org_id` (line 30-32). The `target_project_id` is **supplied by the
caller** (as a URL path segment, ultimately) — the key itself carries no
memory of which project it's "for." Any valid, unexpired, unrevoked key
from org X can authenticate against **any** project belonging to org X by
simply being presented alongside that project's id.
`resolveProjectAccess()` (`project.ts:114-127`) is the entry point routes
actually call — tries the `vlk_` bearer path first, falls back to
Supabase-session-based resolution for the dashboard's own browser calls.

## 17. Local Data Plane architecture

**Verified** (already established earlier this session, re-confirmed):
HTTP request → `auth_guard_v2` middleware (§7a) → handler in `server.rs` →
`SharedEngine` (`RwLock<KernelState>`) → kernel apply → WAL append → BLAKE3
chain update. One `valori-node` process = one project's data, full stop —
there is no multi-tenancy inside a single node process.

## 18. Cloud Data Plane architecture

**Verified.** External client → `valori-ui/ui`'s Next.js API route →
`resolveProjectAccess()`/`proxyToNode()` (§7b, §8) → plain HTTP `fetch()` to
that project's `node_url` → **the same `valori-node` binary from
Valori-Kernel**, unmodified, running in a container the Rust backend
provisioned. The node itself is completely unaware it's "in Cloud mode" —
it has no `vlk_` key logic, no `org_id`, nothing. All multi-tenancy
enforcement happens one hop earlier, in the Next.js proxy layer + Postgres
RPC. This means: **whatever new project-scoped key system gets built, the
node's own local auth (§7a) is a separate, independent gate that Cloud
traffic currently bypasses entirely** (the proxied `fetch()` calls carry no
`Authorization` header of the node's own kind — confirmed by
`nodeProxy.ts:33-36` passing through only `init`, which callers construct
from the original request, not from any node-local token).

## 20. Do Cloud API requests eventually reach `valori-node`?

**Verified — yes**, exactly as described in §18. This is the load-bearing
fact for the whole design: **there is only one data plane binary

the node (as opposed to only at the Next.js proxy hop) must be built as

does not (its key store has no project concept, and Cloud doesn't send it

## Gaps relative to the requested project-scoped model

1. **No `project_id` column on any API-key table anywhere.** Cloud's
   `api_keys` is org-scoped; local's `KeyStore` has no project concept at
   all (a node *is* implicitly one project, but nothing enforces or
   records that).
2. **`ProjectId` (the `valori-domain` newtype meant to unify this) is
   unused in production code.** Building the new system on top of it means
   also finishing the M2 migration `ARCHITECTURE_AUDIT.md` already
   describes, at least for the API-key-adjacent slice.
3. **No expiry mechanism exists anywhere** — must be built from scratch on
   both local and Cloud sides.
4. **The node itself cannot enforce "this key is scoped to project X"**
   because Cloud traffic reaches it through a proxy that already stripped
   any Cloud-specific auth context (§18/§20) — enforcement today is
   100% at the Next.js/Postgres layer, never inside `valori-node`. A design
   that wants defense-in-depth (node also checks project scope, not just
   the proxy) needs new plumbing to get a Cloud-issued, project-scoped
   credential in front of the node in a form it can verify — which
   `valori-node` cannot do today since it has no knowledge of Supabase.
5. **Two incompatible scope vocabularies** (3-tier enum vs. `text[]`) would

6. **No rate limiting, no OpenAPI docs, no project-scoped SDK support**

## Recommended architecture (proposal only — not started)

Given §18/§20 (one data-plane binary, two front doors) and the explicit
public/private boundary from the request:

- **New `project_id uuid` column on Cloud's `api_keys`** (not a new table —
  extend the existing one), `not null references projects(id)`,
  replacing the org-level scoping in `verify_api_key()`'s project lookup
  with a direct `key_row.project_id = target_project_id` check. This is a
  schema migration + one RPC rewrite, both squarely inside `valori-ui`
  (private) — no public-repo change needed for this half.
- **Project creation must issue the first key automatically** — likely a
  trigger or an RPC extension on whatever creates a `projects` row today,
  returning the plaintext key alongside the created project exactly once
  (matching the existing reveal-once convention already used for manual
  key creation).
- **Local/Studio key scoping**: since one node already equals one project,
  the *simplest* correct move is likely "no change needed" for the
  project-scoping question itself — `valori-node`'s `KeyStore` already
  can't leak across projects, because there's only ever one project per
  process. The real local-side gap is narrower: add `expires_at` to
  `ApiKeyRecord` (finding §23) if expiry is wanted locally too.
- **The SDK-facing surface** (§14) needs a decision, not just code: does
  the Python SDK gain a Cloud-specific client mode that sends
  `target_project_id` the way `resolveProjectAccess()` does, or does Cloud
  instead mint a per-project local-format `vk_...` key and hand it to the
  provisioned node at boot (making the node's existing `auth_guard_v2`
  the single enforcement point everywhere, local and Cloud alike, and
  retiring the org-scoping gap in `verify_api_key()` by construction rather
  than by adding a new column)? **This is the single biggest open design
  fork** and should be resolved with the user before any implementation
  starts — it changes whether work happens mostly in `valori-ui`
  (extend `verify_api_key()`) or mostly in `valori-node`
  (teach the node to accept/mint project-scoped credentials directly).
