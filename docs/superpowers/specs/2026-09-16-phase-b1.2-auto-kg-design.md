# Phase B1.2 — Automatic KG Construction Benchmark (Arm C)

## Question this phase answers

Starting from the exact same raw SciFact text used in B1.1, can an automatically constructed graph recover some of the retrieval improvement provided by B1.1's oracle SciFact graph?

```
A  Vector             0.925 Recall@10   (frozen, B1.1)
B  Oracle Graph       0.950 Recall@10   (frozen, B1.1)
C  Auto-KG            ???
```

This document is the investigation + design required before any implementation, per the standing instruction: if integration requires an LLM/API credential or a new heavyweight dependency, stop after this document and report exactly what's required. That condition was met (every extraction path in `neo4j-graphrag` needs either an LLM credential or a new dependency) — the choice was presented and resolved: **a custom non-LLM spaCy-based extractor**, no credential, no API cost. See "Dependency audit and decision" at the end for the full comparison. Nothing beyond this document has been implemented yet.

## Investigation — neo4j-graphrag v1.19.0 (current, as of this phase)

Checked against PyPI metadata and the actual source at `github.com/neo4j/neo4j-graphrag-python` (`src/neo4j_graphrag/components/{types,entity_relation_extractor,kg_writer}.py`), not just doc prose, since the docs paraphrase loosely in places (e.g. an older "experimental" module path no longer matches `main` — components now live at `neo4j_graphrag.components.*`, not `neo4j_graphrag.experimental.components.*`).

**Package**: `neo4j-graphrag` 1.19.0, `requires-python >=3.10,<3.15`. Core (always-installed) deps: `neo4j>=5.28.4,<7.0.0` (the Bolt driver library — a Python package, not a running server), `pydantic`, `numpy`, `scipy`, `pypdf`, `tenacity`, etc. LLM providers are **all opt-in extras**: `neo4j-graphrag[openai]`, `[anthropic]`, `[google-genai]`, `[bedrock]`, `[cohere]`, `[mistralai]`, `[ollama]`. There is also an `[nlp]` extra pulling `spacy==3.8.7`, but that's used elsewhere in the library (e.g. a semantic entity-resolution matcher), not for extraction.

**Data types (from `components/types.py`), confirmed field-for-field:**
```python
class TextChunk(BaseModel):
    text: str
    index: int
    metadata: Optional[dict[str, Any]] = None   # <- we can stash our own document_id here
    uid: str = Field(default_factory=lambda: str(uuid.uuid4()))

class TextChunks(DataModel):
    chunks: list[TextChunk]

class Neo4jNode(BaseModel):
    id: str
    label: str
    properties: dict[str, PropertyValue] = {}
    embedding_properties: dict[str, list[float]] = {}

class Neo4jRelationship(BaseModel):
    start_node_id: str
    end_node_id: str
    type: str
    properties: dict[str, PropertyValue] = {}
    embedding_properties: dict[str, list[float]] = {}

class Neo4jGraph(DataModel):
    nodes: list[Neo4jNode] = []
    relationships: list[Neo4jRelationship] = []
```

**No Neo4j database is required for extraction.** `LLMEntityRelationExtractor.run(chunks=...)` runs fully in-memory and returns a `Neo4jGraph` object — no driver, no server. A driver is only imported/needed by `KGWriter` (`components/kg_writer.py` imports `neo4j` at module level and calls into it for persistence) and by the built-in entity-resolution components (`SinglePropertyExactMatchResolver(driver)` etc., which read/merge nodes against a live database). **We do not need either of those** — see Architecture below.

**LLM providers with documented structured-output support**: `OpenAILLM` (needs `OPENAI_API_KEY`), `AnthropicLLM` (needs `ANTHROPIC_API_KEY`), `VertexAILLM` (needs Google Cloud credentials). No first-class Ollama/local-model path for structured extraction is documented.

## Architecture

Per the standing instruction, this stays entirely outside the kernel/node — Neo4j types never reach `valori-kernel`, `valori-node`, or any production API:

```
SciFact raw text (same 300 docs + same 100 claims as B1.1, same IDs)
        │
        ▼
TextChunks: one TextChunk per document/claim (document-level chunking,
matching B1.1's existing granularity exactly -- no new chunking variable)
metadata={"source_id": <same id used in B1.1's rec_to_doc/doc_to_node maps>}
        │
        ▼
SpacyEntityRelationExtractor.run(chunks)   # our subclass of EntityRelationExtractor
   -- noun-chunk entities + SVO-heuristic relations, see below
   -- no LLM, no credential, fully offline and deterministic
        │
        ▼
Neo4jGraph (nodes + relationships, in-memory, no driver, no Neo4j server)
        │
        ▼
LEAKAGE GUARD (fail loud) -- see below
        │
        ▼
benchmarks/autokg_adapter.py: Neo4jGraph -> co-mention collapse -> Valori mutations
                                          -> full extracted graph -> provenance sidecar
        │
        ├──▶ Existing Valori HTTP API: POST /v1/graph/edge -- ONLY the collapsed
        │    co_mentions_entity direct claim<->document edges (see "the one real
        │    design decision" below). No new entity nodes are created in Valori;
        │    reuses the exact same 400 chunk nodes already inserted for the
        │    B1.1-identical vector ingest. No new endpoints, no kernel schema change.
        │
        └──▶ benchmarks/public-data/scifact/auto_kg_graph_b1_2.json -- the FULL
             extracted graph (all entity nodes, all intra-chunk relations, all
             provenance) for graph-quality evaluation and construction stats.
             This richer graph is never sent to Valori.
        │
        ▼
Existing /v1/graphrag, same retrieval_k/final_k/depth/graph_weight as B1.1
```

**Two different graphs, on purpose.** The *extracted* graph (entities + intra-chunk relations like `TREATS`/`CAUSES`) is the thing being evaluated for quality — it lives only in the sidecar JSON. The *Valori-inserted* graph is just the derived `co_mentions_entity` direct edges between claim and document chunk-nodes — structurally identical in shape to B's oracle graph (same 400 pre-existing nodes, only new edges differ), which is what keeps A/B/C actually comparable through the same `depth=1` GraphRAG call. Conflating the two would either bloat Valori with entity nodes that have no oracle-graph analog (confounding the comparison) or lose the entity-level detail needed for graph-quality evaluation.

### The one real design decision: bridging extracted entities to GraphRAG's 1-hop traversal

This is the crux of the whole experiment, and it's not covered by simply "call the extractor" — it determines whether arm C can score *anything* above arm A regardless of extraction quality, so it needs to be stated explicitly and frozen before results are seen.

B1.1's oracle graph connects a claim directly to its evidence document (`claim --[EDGE]--> document`), so GraphRAG's `depth=1` traversal reaches evidence in one hop. An entity-extraction graph naturally produces `claim --[MENTIONS]--> entity <--[MENTIONS]-- document` — **two hops**, not one. Per the standing instruction, GraphRAG parameters (including `depth=1`) must stay identical to B1.1 and must not be tuned. If arm C's graph is left in that native two-hop shape, `depth=1` GraphRAG would never reach a single evidence document through it, and arm C would trivially score ≈ arm A — not because automatic extraction is bad, but because of a topology mismatch with the fixed `depth=1` parameter. That would be measuring the wrong thing.

**Design decision**: after extraction, the adapter collapses shared-entity mentions into a direct edge: if a claim chunk and a document chunk both produced a `MENTIONS` relationship to an entity node with the same normalized name (case-insensitive exact match on `Neo4jNode.properties["name"]` — a simple, undocumented-elsewhere, in-adapter dedup that needs no Neo4j database), the adapter creates one direct `co_mentions_entity` edge between the claim's Valori node and the document's Valori node. This mirrors the oracle graph's direct-edge shape, keeps `depth=1` traversal semantics identical between B and C, and isolates the actual experimental variable (whether automatic extraction identifies genuine claim–evidence connections) rather than an artifact of graph depth. This rule is frozen here, before any arm-C numbers exist — it is not tuned after seeing results.

### Extraction logic (frozen before any run) — `SpacyEntityRelationExtractor`

A subclass of `neo4j_graphrag.components.entity_relation_extractor.EntityRelationExtractor`, using `spacy` + `en_core_web_sm` (no LLM). `en_core_web_sm`'s default NER labels (PERSON/ORG/GPE/DATE/...) are tuned for news text and are a poor fit for biomedical abstracts, so entities are extracted as **noun chunks** (`doc.noun_chunks`) rather than named entities — a standard lightweight technique that captures domain phrases like "abnormal accumulation of lipids" or "type 2 diabetes" that generic NER would miss entirely:

- **Entities**: each `doc.noun_chunk` is kept if, after lowercasing/stripping, it has ≥3 characters and is not entirely stopwords/pronouns. Node label is uniformly `"Concept"` (spaCy's NER types aren't reliable enough here to justify finer labels — a known limitation, not hidden; a specialized biomedical NER model would be the natural follow-up if this experiment shows promise). `properties.name` is the normalized chunk text; `properties.raw_text` keeps the original casing/span for provenance.
- **Relations**: per sentence, walk the dependency parse for a subject–verb–object pattern (`nsubj`/`nsubjpass` → governing `VERB` → `dobj`/`pobj`/`attr`) where both the subject and object overlap a kept noun chunk. Creates `Neo4jRelationship(type=<verb.lemma_.upper()>, start=subject_entity, end=object_entity)`. Sentences with ≥2 kept noun chunks but no SVO match instead get a generic `CO_OCCURS_WITH` edge between the first two chunks in sentence order — a defensible, common fallback, not a claim of a real semantic relation.
- No entity resolution beyond exact normalized-string match (see the co-mention collapse step) — no fuzzy matching, no embeddings-based merge. This is deliberately the simplest correct thing, consistent with "no generative LLM."

This logic is written once, frozen, and never adjusted after seeing arm-C's numbers. The chosen approach (noun chunks + SVO heuristic vs. e.g. plain NER) is recorded in the run's `meta` block so it's inspectable.

## Critical leakage rule — enforcement design

Requirement: during graph construction, arm C must have zero access to qrels, evidence doc IDs, rationale sentence IDs, SUPPORT/CONTRADICT labels, or B1.1's oracle edges. SciFact annotations load only after C's graph is frozen, for evaluation.

Enforcement (fail loud, not just "be careful"):
1. **Module boundary**: extraction lives in a new `benchmarks/autokg_extract.py` that takes only `(chunk_id, text)` pairs as input — its function signature has no parameter through which `qrels` or `queries[q]["metadata"]` could be passed, by construction.
2. **Runtime guard**: a `assert_no_leakage(chunks)` function scans every `TextChunk.metadata` dict (and the schema/examples strings passed to the extractor) for a blocklist of keys/substrings — `qrel`, `evidence`, `rationale`, `support`, `contradict`, `oracle`, `sufficient_label` — and raises `AssertionError` if any are found. Called immediately before `extractor.run(...)`.
3. **Test**: a unit test asserts `assert_no_leakage` raises when a chunk's metadata is deliberately seeded with an `evidence_doc_id` key, and does not raise on the real chunk construction path.
4. **Ordering**: `download()` (which loads `qrels`) is still called once at the top of `main()` for the *retrieval* evaluation, exactly as in B1.1 — but the value is not threaded into the extraction call at all, and the leakage guard would catch it if a future edit accidentally did.

## Provenance

Every automatically generated edge keeps, in a sidecar file (not sent to Valori — the kernel edge schema is not touched):

```json
{
  "source_id": "<document or claim id>",
  "source_entity": "<Neo4jNode.properties.name for the start entity, or null for a co_mentions_entity edge>",
  "target_entity": "<...>",
  "relationship_type": "<Neo4jRelationship.type ('CO_OCCURS_WITH' or an SVO verb lemma), or 'co_mentions_entity'>",
  "extractor": "benchmarks.autokg_extract.SpacyEntityRelationExtractor",
  "extractor_version": "<spacy version>+<en_core_web_sm version>",
  "confidence": null
}
```
`confidence` is `null` because the SVO/noun-chunk heuristic has no probabilistic score to report — stated as `null`, not fabricated.

## Metrics (arm C, identical implementation to A/B)

Reuses `metrics()`, `latency_stats()`, and `validate_ab()` from B1.1 unchanged — `validate_ab()` already iterates every key under `out["systems"]`, so adding `valori_http_vector_autokg` requires no changes to the validator itself, only to `main()`'s wiring. Same `Recall@3/5/10`, `nDCG@3/5/10`, `MRR@10`, `CompleteContext@10`, latency mean/p50/p95/p99.

**Auto-KG construction stats** (new block, alongside the existing `ingestion` block): nodes generated, edges generated, relationship-type counts, isolated-node count, duplicate/merged-entity count (from the co-mention collapse step), rejected-relationship count (if the extractor's `on_error=OnError.IGNORE` path drops any), extraction duration, graph-build duration. `model/API usage` and `estimated/actual extraction cost` are reported as `spacy/en_core_web_sm (local, offline)` and `0` respectively — there is no external API call to meter, and that's itself a real, reportable fact about this arm versus an LLM-based one.

**Graph-quality evaluation** (after C's graph is frozen, using hidden SciFact annotations): the mapping used is *only* the `co_mentions_entity` claim→document edges created by the adapter — these are the sole edges with a direct semantic parallel to SciFact's claim→evidence relation. Arbitrary entity-to-entity relationships (`TREATS`, `CAUSES`, etc.) are not mapped to SciFact's claim/evidence structure at all, because SciFact does not label entity-level relations — computing an edge-F1 against them would be inventing ground truth that doesn't exist. So:
- Where the mapping is valid (`co_mentions_entity` claim→document edges vs. SciFact's claim→evidence qrels): report edge precision, recall, F1.
- For everything else: no edge-F1 is reported. This is stated explicitly in the phase doc rather than silently omitted.

**Recovery**, per retrieval metric where higher is better:
```
auto_gain   = C - A
oracle_gain = B - A
recovery    = auto_gain / oracle_gain      # only when oracle_gain > 0
recovery    = "N/A"                         # when B - A <= 0
```
Not computed for latency. Negative recovery is reported as-is, not hidden. `B` is labeled `oracle_scifact` / "oracle reference" everywhere it's reported — never "ceiling" or "maximum."

## Dependency audit and decision (resolved)

Every extraction path in `neo4j-graphrag` 1.19.0 requires either a new external LLM credential or a new dependency this environment doesn't have — flagged per the standing instruction, and decided as follows:

| Path | New pip deps | Credential needed | Live DB needed | Cost |
|---|---|---|---|---|
| Neo4j KG Builder as shipped — `LLMEntityRelationExtractor` | `neo4j-graphrag[openai]` or `[anthropic]` | `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` — not set in this environment | No | Real, billed: ~400 LLM calls per run | 
| **Chosen: custom non-LLM extractor** — `SpacyEntityRelationExtractor` subclassing `EntityRelationExtractor` | `spacy` + `en_core_web_sm` (~13MB model download, one-time) | None | No | None — offline, deterministic |

**Decision: the custom spaCy-based extractor.** No credential, no per-run API cost, deterministic and reproducible (same input text always yields the same graph — useful for a frozen benchmark artifact). It reuses Neo4j's `Neo4jGraph`/`Neo4jNode`/`Neo4jRelationship` types and the `EntityRelationExtractor` interface contract (the "prefer lower-level extraction interfaces" path), with our own extraction logic behind it rather than Neo4j's shipped LLM-based one. `neo4j-graphrag` itself is still installed (for the `EntityRelationExtractor`/`Neo4jGraph` types and to subclass correctly) — it pulls in the `neo4j` driver package as a transitive dependency (a Python package only, no server), plus `pydantic`/`numpy`/`scipy`/etc. No live Neo4j database is needed either way. Docker is available locally if a live Neo4j database were ever wanted for a different comparison, but this design doesn't need one.
