# Phase B1.1 — Frozen A/B baseline with multi-cutoff metrics

## Purpose

Phase B1 (`docs/phases/phase-B1-live-retrieval-quality-benchmark.md`) proved,
at a single cutoff (`k=3`), that Valori HTTP GraphRAG with SciFact's oracle
claim→evidence edges beats vector-only retrieval on the same data. B1.1
extends the same script so one run reports a richer, frozen metric set at
multiple cutoffs, plus enough reproducibility metadata to serve as a fixed
baseline for the later Auto-KG comparison (B1.2). B1.1 does not change what
is measured conceptually (still vector-only vs. oracle-graph GraphRAG) — it
only widens and hardens how it's measured and recorded.

This is a benchmark-script change, not a Rust/kernel change. It does not
touch `crates/`.

## Scope — unchanged from B1

- 300 SciFact documents (evidence-preserving slice), 100 queries — same
  selection logic already in `live_local_db_comparison.py`.
- Same cached MiniLM embeddings (`all-MiniLM-L6-v2-corpus.npy`,
  `all-MiniLM-L6-v2-test-q100.npy`) — no re-embedding.
- Same Valori node, same index (brute-force default), same HTTP path
  (`valori-http` arm only — the embedded FFI path is skipped; B1 already
  found it doesn't expose graph edges through `get_edges()`/`walk()`).
- Same graph construction: SciFact's public query `metadata` claim→evidence
  pairs become graph edges (`public_claim_edges()`), explicitly labeled
  `oracle_scifact` in the recorded output.
- Same GraphRAG call shape: `retrieval_k=k`, `final_k=k+10`, `depth=1`,
  `graph_weight=0.3` (B1's values, unchanged).

## What changes

### 1. Metrics — `metrics(results, qrels, ks=(3, 5, 10))`

Returns, per system arm:

| Field | Definition |
|---|---|
| `recall_at_3`, `recall_at_5`, `recall_at_10` | `\|top-k ∩ gold\| / \|gold\|`, all three sliced from one top-10 ranked list per query (one retrieval call, not three) |
| `ndcg_at_3`, `ndcg_at_5`, `ndcg_at_10` | Standard DCG/ideal-DCG at each cutoff |
| `mrr_at_10` | MRR@10 — reciprocal rank of first relevant doc in the top-10 list, 0 if absent |
| `complete_context` | Existing field, kept, computed at cutoff 10 (matches B1 semantics) |
| `latency_mean_ms`, `latency_p50_ms`, `latency_p95_ms`, `latency_p99_ms` | Per-query search latency, in milliseconds. Mean is kept (B1 had it) alongside the new percentiles. |
| `query_count` | `len(results)` — sanity/reproducibility field |

Latency is captured by timing each query's HTTP call individually (list of
per-query durations) instead of dividing one wall-clock total by query
count. This applies to both the vector-only loop and the GraphRAG loop in
`valori_http()`. The FAISS and embedded-FFI code paths get the same
`metrics()` call signature so they don't break, but B1.1's actual recorded
run only exercises `valori-http`.

### 2. Output file — do not overwrite B1

`live_local_db_comparison.py` currently always writes
`benchmarks/LIVE_LOCAL_RESULTS.json`. B1.1 adds a `--out` flag (default
keeps today's filename for backward compatibility with any other caller),
and the B1.1 run is invoked with
`--out benchmarks/LIVE_LOCAL_RESULTS_B1_1.json`. The original
`LIVE_LOCAL_RESULTS.json` from B1 is left untouched on disk as historical
evidence.

### 3. Reproducibility metadata

The output JSON gains a `meta` block:

```json
{
  "meta": {
    "phase": "B1.1",
    "git_commit": "<git rev-parse HEAD, captured at run time>",
    "timestamp_utc": "<ISO 8601, captured at run time>",
    "dataset": "BEIR SciFact",
    "documents": 300,
    "queries": 100,
    "embedding_model": "sentence-transformers/all-MiniLM-L6-v2",
    "embedding_dim": 384,
    "index": "valori-http (brute-force default)",
    "graph_source": "oracle_scifact",
    "graphrag_params": {
      "retrieval_k": 10,
      "final_k": 20,
      "depth": 1,
      "graph_weight": 0.3
    },
    "node_version": "<GET /v1/version — confirmed cheap: returns CARGO_PKG_VERSION as plain text>",
    "valori_url": "<the --valori-url used>"
  }
}
```

If a field can't be cheaply obtained (e.g. no `/v1/version` endpoint exists),
fall back to a static/derivable value rather than adding new endpoints —
B1.1 must not require node changes.

### 4. Ingestion stats (opportunistic, not a scope expansion)

Since `valori_http()` already loops over inserts and edge creation, record
the counts and timing it already has for free:

```json
"ingestion": {
  "documents_inserted": 300,
  "vectors_inserted": 400,
  "oracle_edges_inserted": 72,
  "ingestion_duration_s": 12.3
}
```

No new instrumentation beyond what the existing loop already computes
(`build` timer, `graph_edges` counter) — just surface it in the output
instead of dropping it.

## Validation — data/math invariants only

Explicitly **not** a validation check: "graph arm recall ≥ vector arm
recall." A regression is a valid experimental result and must be recorded,
not treated as benchmark failure.

Checks that *are* asserted (fail loud if violated — these indicate a bug in
the metric code, not an experimental outcome):

- `recall_at_10 >= recall_at_5 >= recall_at_3` for every arm.
- **Not asserted:** any ordering across `ndcg_at_3`/`ndcg_at_5`/`ndcg_at_10`.
  nDCG's ideal-DCG denominator changes with the cutoff, so a correct
  implementation is not guaranteed to be monotonic in `k` (e.g. `nDCG@3 =
  0.91, nDCG@5 = 0.87, nDCG@10 = 0.89` is legitimate). Each `ndcg_at_k` is
  still individually bounded to `[0, 1]`.
- All `recall_at_k`, `ndcg_at_k`, `mrr_at_10`, `complete_context` values in
  `[0, 1]`.
- `latency_p99_ms >= latency_p95_ms >= latency_p50_ms`.
- Vector-arm and graph-arm queries are the exact same 100 query IDs (same
  `selected` list already guarantees this — assert `set(vector_results) ==
  set(graph_results)`).
- `query_count == 100` for both arms.

`cargo test -p valori-kernel -p valori-node` still runs per the standard
phase checklist even though no Rust code changes, since it's the mandatory
gate for every phase.

## Explicitly out of scope for B1.1

- Auto-KG / Neo4j KG Builder integration — that's B1.2, and it must be built
  so the extraction pipeline never sees SciFact's evidence annotations
  (those are only used afterward, for evaluation and for the
  Recovery = (C−A)/(B−A) metric).
- Any GraphRAG parameter tuning based on B1.1's results. B1.1 is frozen once
  recorded — no adjusting `depth`/`graph_weight`/edge filters afterward in
  response to what the numbers show.
- FAISS/Qdrant/Milvus/Weaviate baselines (B2's territory per the original
  B1 follow-ups).
- New node HTTP endpoints. If node-version metadata isn't cheaply available,
  record what's derivable instead rather than adding an endpoint.
